# Colors

> El color crea jerarquía. No decoración.
> 90% de la interfaz Medmo es neutral. El color aparece solo donde comunica significado.

---

## Design Intent

Esta sección explica **por qué** existe el Color System — no qué contiene. Toda decisión de color en Medmo debe poder trazarse a uno de estos principios.

### El color comunica significado, no decoración

Medmo es una plataforma de trabajo clínico, no un producto de marketing. El color aparece cuando tiene un **rol semántico**: indicar una acción, un estado, un error, una selección. Si un elemento puede funcionar igual en neutral, debe ser neutral.

**Implicación:** El 90%+ de la interfaz es escala neutral. Primary, Success, Warning, Error e Info existen porque comunican algo al usuario — nunca porque "se ve bien."

### La jerarquía se construye principalmente con espacio

En interfaces de larga duración, la diferencia entre un heading y body text no debe depender del color. La jerarquía tipográfica (peso, tamaño) y el espaciado (Spacing Foundation) son los protagonistas. El color refuerza, no lidera.

**Implicación:** `color-text-primary` y `color-text-secondary` usan la escala neutral, no primary. No pintamos headings de azul navy para "darles importancia."

### Las superficies crean profundidad

Medmo no usa sombras pesadas para comunicar capas. La profundidad viene de la **jerarquía de superficies**: Background → Surface → Surface Raised → Surface Floating → Overlay. Cada nivel es un tono diferente, no un efecto decorativo.

**Implicación:** Un dropdown no flota porque tiene sombra dramática — flota porque usa `color-surface-floating` sobre `color-background`. La sombra, cuando existe, es casi imperceptible ([Shadows Foundation](./shadows.mdx)).

### Nunca usamos color únicamente por razones estéticas

Si la única razón para aplicar un color es "que se vea más moderno" o "que destaque más", esa razón no es válida en Medmo. Cada token de color debe responder: **¿qué le comunica esto al usuario?**

**Implicación:** No hay "accent colors" decorativos. No hay gradientes. No hay colores de sección para variar visualmente entre pantallas. La consistencia reduce carga cognitiva.

## Filosofía

El Color System de Medmo está diseñado para **jornadas de 8+ horas**. Cada decisión prioriza:

- **Legibilidad** — contraste WCAG AA verificado en cada par
- **Baja fatiga visual** — cromas contenidos, neutrals dominantes
- **Estados claros** — feedback con tokens dedicados, nunca color solo
- **Consistencia** — componentes consumen solo tokens semánticos

**Color primario:** `#242F50` (primary-800) — nunca modificar sin autorización.

## Arquitectura

```
Primitives (interno)     Semantic Tokens (componentes)     CSS Variables (runtime)
─────────────────────    ─────────────────────────────     ──────────────────────
primary-800           →  color-action-primary           →  --color-action-primary
neutral-800           →  color-text-primary             →  --color-text-primary
success-700           →  color-success-text             →  --color-success-text
```

**Regla:** Los componentes **nunca** consumen primitivos. Solo `--color-*` y `--focus-*`.

## Jerarquía de Superficies

Profundidad por tono, no por sombra. Inspirado en IBM Carbon y Material 3.

| Nivel | Token | Hex (light) | Propósito |
|-------|-------|-------------|-----------|
| 0 | `color-background` | `#F9FAFB` | Canvas de página |
| 1 | `color-surface` | `#FFFFFF` | Cards, panels |
| 2 | `color-surface-raised` | `#FFFFFF` | Contenedores anidados |
| 3 | `color-surface-floating` | `#FFFFFF` | Dropdowns, popovers |
| 4 | `color-overlay` | `#121620` @ 40% | Backdrop de modales |

### color-background

**Propósito:** Canvas base de toda pantalla.

**Usar en:** Fondo de la aplicación, área principal detrás de cards.

**No usar en:** Cards, inputs, dropdowns, modales.

<div style={{ background: '#F9FAFB', border: '1px solid #D5D7DD', borderRadius: '8px', padding: '24px', marginBottom: '8px' }}>
  <span style={{ color: '#343842', fontSize: '14px' }}>Page background — neutral-50</span>
</div>

### color-surface

**Propósito:** Contenedor de contenido sobre el background.

**Usar en:** Cards, panels, secciones de formulario, contenido de modales.

**No usar en:** Fondo de página, elementos flotantes.

<div style={{ background: '#FFFFFF', border: '1px solid #B5B7BE', borderRadius: '8px', padding: '24px', marginBottom: '8px', boxShadow: '0 1px 2px rgba(0,0,0,0.04)' }}>
  <span style={{ color: '#343842', fontSize: '14px' }}>Surface — white card on background</span>
</div>

### color-surface-floating

**Propósito:** Elementos desprendidos que flotan sobre la página.

**Usar en:** Dropdown menus, popovers, select content, tooltips.

**No usar en:** Cards estáticas, secciones de página.

<div style={{ background: '#FFFFFF', border: '1px solid #B5B7BE', borderRadius: '8px', padding: '16px', marginBottom: '8px', boxShadow: '0 4px 6px rgba(0,0,0,0.06)' }}>
  <span style={{ color: '#343842', fontSize: '14px' }}>Surface floating — dropdown/popover</span>
</div>

### color-overlay

**Propósito:** Capa semi-transparente que oscurece el contenido detrás de modales.

**Usar en:** Dialog backdrop, drawer backdrop, loading overlay.

**No usar en:** Fondos sólidos, cards.

## Interaction Tokens (planificado)

> **Estado:** Documentado — no implementado.
> Ver [Blueprint — Interaction Tokens](../blueprint.mdx#interaction-tokens-planificado).

Los Semantic Tokens actuales (`color-action-primary`, etc.) definen **qué color** usar. Los **Interaction Tokens** definirán **cómo se comporta** un elemento en cada estado interactivo — consumidos directamente por componentes.

```
Semantic Tokens          Interaction Tokens (futuro)         Componentes
────────────────         ───────────────────────────         ───────────
color-action-primary  →  interaction-action-default     →   Button
                         interaction-action-hover
                         interaction-action-pressed
                         interaction-action-disabled
```

| Token (planificado) | Propósito | Deriva de |
|---------------------|-----------|-----------|
| `interaction-action-default` | Estado reposo de acciones primarias | `color-action-primary` |
| `interaction-action-hover` | Hover sobre acciones | `color-action-primary-hover` |
| `interaction-action-pressed` | Estado activo/pressed | `color-action-primary-active` |
| `interaction-action-disabled` | Acciones deshabilitadas | `color-disabled-*` |

**Por qué una capa separada:** Un Button no debe conocer qué primitivo es `primary-800`. Tampoco debería mapear manualmente hover → `color-action-primary-hover`. Los Interaction Tokens encapsulan la máquina de estados completa. Un Switch, un Checkbox y un Button comparten la misma lógica de interacción sin duplicar CSS.

**Cuándo:** Fase de Primitives, cuando personalicemos Button, Input y controles interactivos.

| `data-status-cancelled` | Cancelado/anulado |
| `data-status-in-progress` | En curso |

**Por qué separados de Success/Warning/Error:** "Pending" no es un warning. "Escalated" no es un error. Los estados de negocio tienen significado clínico propio que no debe colisionar con feedback de UI. Un badge "Pending" y un banner de error pueden coexistir en la misma vista sin ambigüedad.

**Cuándo:** Fase de Domain Components o Patterns (DataTable), cuando definamos columnas de estado clínico.

## Reglas de uso

Ver `foundations/colors/rules.md` para la guía completa.

**DO:** Semantic tokens, focus tokens, pares documentados.

**DON'T:** Primitivos en componentes, hex hardcodeado, opacity para disabled, focus per-component.
